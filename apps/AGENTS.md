# Application Agent Rules

本文件适用于 `apps/**`，补充仓库根目录的总体架构原则。具体应用的 `AGENTS.md` 可继续收紧实现规则。

## 工具链与依赖

- 只使用 pnpm；禁止使用 npm、yarn、bun，也不要生成其他包管理器的锁文件。
- 运行环境目标为 Node.js `>=26.7.0 <27`、pnpm `>=11.20.0 <12`。所有安装命令从仓库根目录执行。
- 内部依赖使用 `workspace:*`；外部依赖使用精确版本，不使用 `^`、`~` 或 `latest`。添加依赖时使用精确 workspace 过滤器，例如 `pnpm --filter @chat-to-video/api add -E <package>@<version>`。
- Windows PowerShell 若因执行策略无法运行 `pnpm.ps1`，使用 `pnpm.cmd` 或 `corepack pnpm`，不得修改机器级执行策略。
- 不手工编辑 `pnpm-lock.yaml`，也不提交 `.env`、密钥、签名 URL、媒体产物、临时目录、构建目录或依赖安装产物。

## TypeScript 与代码组织

- 保持 `strict` 和 `noUncheckedIndexedAccess`；不得用 `any`、非空断言或关闭规则掩盖类型问题。未知边界输入使用 `unknown`，经 Schema 校验后再收窄。
- 使用所在 workspace 的 ESM/NodeNext 或 Next.js Bundler 约定，不把 Node-only 模块带入客户端组件。
- 优先小而清晰的领域模块和显式依赖注入。控制器或路由只负责协议转换，核心业务进入 service/use-case，外部系统通过 adapter 封装。
- 对外导出保持最小化，通过共享包公共入口导入；避免跨包深路径导入。
- 命名表达业务含义；布尔值使用 `is/has/can/should` 前缀，时间值写明单位，ID 不混用。注释解释约束和原因，不复述代码。
- 不顺手格式化或重写无关文件；保留用户已有改动、换行和编码风格。

## 边界校验与失败处理

- 客户端输入、队列载荷、模型输出、环境变量和外部服务响应均视为不可信，在应用自身的信任边界重新解析共享 Schema。
- 变更环境变量时同步更新根目录 `.env.example` 和应用配置校验，只填写安全占位值。
- Agent、模型网关或工作流发生无法提供有效结果的内部错误时，不得向用户暴露原始异常、内部错误码或诊断详情，也不得额外渲染破坏消息流的错误卡。
- 服务端须持久化真实失败状态、受控 failure code、脱敏诊断和审计记录；用户侧通过正常 Assistant 消息持久化与 SSE 完成通道幂等返回固定文案“服务器连接错误，请稍后重试。”。可操作的输入校验、审批、能力缺失或业务阻塞仍返回对应受控提示。

## 测试与验证

- 修复缺陷时先补能复现问题的测试；新增行为至少覆盖成功路径、输入校验和关键失败路径。
- 纯逻辑优先单元测试，API 边界使用集成测试，跨 Web/API/Worker 的关键链路放在根目录 `tests/e2e`。外部模型、S3、Redis、数据库和媒体进程在单元测试中通过接口替身隔离。
- 除非用户明确要求，不得自行启动应用或基础设施，不得运行测试、构建、Docker 镜像构建或 `docker compose up`。
- 实现完成后只执行改动 workspace 的静态检查，通常依次为 `pnpm --filter <workspace> typecheck` 和 `pnpm --filter <workspace> lint`。
- 测试和构建仍应随实现维护；完成报告必须明确已执行的静态检查，以及未运行的测试、构建和启动验证，不得把静态检查描述为测试或构建通过。

## 工作流程

- 修改前检查 `git status`、相关源码、配置和测试；不得覆盖、回退或清理用户已有改动。
- 先定位受影响 workspace 和公共边界，再做满足任务的最小改动。引入依赖前先确认现有依赖或平台能力能否满足。
- 行为、启动方式或架构边界变化时同步更新对应文档。
- 只有实现、相关测试和必要文档一致，且没有遗留静默失败时，才将任务视为完成。
